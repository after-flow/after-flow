# ADR 0001: Firebase Authenticationを採用し、案件の認可をBackendで管理する

- 状態: 部分決定（Provider・利用方針は決定。実接続の詳細は「未決事項」に記載）
- 作成日: 2026-09-20
- 更新日: 2026-09-21
- 関連Issue: #6、#127、Frontend #90、#92

## 背景

従来のADRでは、認証Providerの選定を保留し、token検証をIdentity Adapterへ隔離していた。今回、GCPへ運用を統一する方針に基づき、Firebase Authenticationを採用する。

after-flowでは、利用者が自分の案件を作成し、家族を招待して共同利用する。同じ利用者が複数案件に参加し、案件ごとに異なる権限を持つ。このため、アカウントの認証と、対象案件へのアクセス権限を分けて管理する。

本ADRは判断内容と認証・認可の基本契約を記録する。コード実装、Firebaseの設定、実接続・staging検証の完了を示すものではない。

## 決定

### 1. 認証Providerとログイン方法

- Firebase Authenticationを採用する。
- 初期版のログイン方法は、Googleログインとメールアドレス・パスワードとする。
- メールアドレスの確認を必須とする。
- パスワードの保存・検証・再設定はFirebaseに任せ、自前のパスワードDBを作らない。
- 初期版では二段階認証を導入しない。MFAを目的としたIdentity Platformへのアップグレードも行わない。他の要件で必要になる場合は別途判断する。
- 任意のメールアドレス・パスワードで成功する旧 `/auth/login` のモックを、実認証として移植しない。

### 2. 利用者登録・認証・案件の認可

- 誰でもアカウントを登録し、自分の案件を作成できる。初回登録に運営からの招待を必要としない。
- Firebaseはアカウントを認証し、BackendはFirestoreのmembershipを根拠として、対象tenant・Caseへの所属と操作権限を確認する。
- 認証済みの `uid/sub` を利用者の識別子として扱う。要求本文のuserIdや、メールアドレスだけを認証の根拠にしない。
- 業務tenantやCase roleを、Firebaseのログインtokenのcustom claimへ埋め込む方式は採用しない。従来の「tenant claimを必須にする」前提を変更する。
- 1つのアカウントで複数案件に参加でき、管理者・編集・閲覧の権限は案件ごとに設定する。
- リクエストが指定したCaseやtenantは対象を選ぶための情報として扱い、権限の証明には使わない。Backendが保存済みmembershipを確認して実行文脈を導出する。
- 所属・権限の付与と変更はBackendが制御する。家族情報への登録やTask担当者の指定だけでは、ログイン権限を付与しない。
- 現行の「案件作成者をOWNERにする」境界を維持する。アカウントとCase内Personの本人紐付けは別の契約として扱う。

ここでいう認証はアカウントの確認であり、相続人資格や代理権等を確認・確定するものではない。

### 3. 家族の招待と共同利用

初期版から家族の招待・共同利用を提供する。家族はそれぞれ自分のアカウントで参加する。

| 項目 | 決定内容 |
|---|---|
| 招待者 | 対象案件の管理者 |
| 招待方法 | メールアドレスを指定して招待する |
| 付与する権限 | 管理者が招待時に「閲覧のみ／編集可能」を選ぶ |
| 参加条件 | 招待先と同じメールアドレスを確認済みのアカウントでログインし、本人が招待を受諾する |
| 有効期限 | 発行から7日間 |
| 受諾回数 | 一度だけ。重複要求で権限を重複付与しない |
| 取消・再発行 | 管理者が未受諾の招待を取り消し・再発行できる。再発行時は古い招待を無効化する |
| 宛先が異なる場合 | 正しいメールアドレス宛てに招待し直す |

アカウント登録と、他人が作成した案件への参加権限は別に扱う。招待リンクを開いただけでは参加させない。編集権限への招待を、管理者権限の譲渡や他人の本人専用操作の許可として扱わない。

### 4. ログイン維持・更新・再認証

- ログイン状態は、ログインまたは再認証から最長7日間維持する。
- 通常利用やtokenの自動更新だけでは7日間の上限を延長しない。上限に達した場合は再ログインを要求する。
- Firebase ID token自体の有効期限・更新と、after-flowのログイン維持上限を区別する。7日間の上限はBackendでも検証する。
- 招待や権限変更等の重要操作に対して、アプリ独自の「直近5分以内のログイン」等の再認証条件は追加しない。
- パスワード変更等でFirebaseが要求する再認証には従う。重要操作の再認証を追加しない方針とは別に、通常の認証、案件の認可、期限、失効確認を適用する。

### 5. ログアウト・失効・アカウント停止

| 場面 | 決定内容 |
|---|---|
| 通常ログアウト | 操作したブラウザをログアウトさせる。他の端末のログインは維持する |
| 全端末からログアウト | 初期版から本人が選べる機能として提供する。全端末の既存の認証を失効させ、再ログインを必要とする |
| パスワード再設定 | 全端末の既存の認証を失効させる |
| アカウント停止 | 停止したアカウントからのBackendへのアクセスを拒否する |

ブラウザ内の認証状態の破棄と、発行済みtokenの失効は区別する。Backendは失効・停止を確認し、署名と有効期限が正しいだけではアクセスを許可しない。案件からの除外・権限変更は、アカウント全体の失効とは分けてmembershipへ反映する。

失効の契約はBackendへのアクセスを対象とする。表示済み情報の遠隔消去や、進行中の非同期処理の取消までを、このADRで保証するものではない。

### 6. 維持する設計上の制約

- token検証はIdentity Adapterへ隔離する。ApplicationはProvider固有のissuer、署名検証、鍵取得処理へ直接依存しない。
- 認証設定がない場合に検証を省略して通す既定値を作らない。保護APIを全拒否する既存方針を維持する。
- `none` や対称鍵方式をFirebase ID tokenの検証方式として許可しない。
- 業務データとmembershipの正本はBackendが管理するFirestoreとする。ブラウザやAIの自己申告で所属・権限を確定しない。

## 採用理由と選択肢

| 選択肢 | 判断と理由 |
|---|---|
| Firebase Authentication | 採用。GCPへ運用を統一する方針に合わせる |
| Firebase Authentication with Identity Platformへのアップグレード | 今回は選択しない。初期版ではMFAを導入せず、アップグレードを必要とする他の要件も今回の判断では確定していない |
| Clerk、Auth0、Amazon Cognito、Supabase Auth、Keycloak | 今回は採用しない。GCPへの運用統一を優先したためであり、各製品が認証要件を満たせないと評価したものではない |
| 業務tenantをtokenのclaimに持たせる方式 | 採用しない。複数案件への参加と案件ごとの権限を、Backendの保存済み所属から判断する方針を選択した |
| 自前のパスワードDB・成功固定ログイン | 採用しない。資格情報の管理をFirebaseに委ね、開発用モックを本番認証にしない |

MFAと重要操作向けの独自再認証を初期版に含めないことも今回の選択である。メール確認、7日間の上限、失効確認、membershipによる認可はそれぞれ維持する。

## Firebase接続条件と未決事項

採用Providerに合わせる接続条件は以下とする。環境ごとの実値やAdapterの具体方式まで決定済みと扱わない。

| 項目 | 接続条件 |
|---|---|
| Backendへ提示するtoken | Firebase Client SDKから取得するFirebase ID token |
| issuer | `https://securetoken.google.com/<projectId>` |
| audience | 対象環境のFirebase project ID |
| 許可algorithm | `RS256` |
| 利用者識別 | 検証済み `uid/sub` |
| 業務tenant claim | 使用しない。対象tenant・CaseのmembershipをBackendで確認する |

issuer・audience・署名方式等は [FirebaseのID token検証仕様](https://firebase.google.com/docs/auth/admin/verify-id-tokens) に基づく。署名・期限の検証に加え、合意した失効動作を満たす必要がある。[Firebaseのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions)

次は未決事項として残す。判断済みの利用方針を変更しない範囲で、実装前に具体化する。

| 未決事項 | 検討内容・制約 |
|---|---|
| token検証Adapter・鍵取得方式 | Firebase Admin SDKを既存TokenVerifierのAdapterとして使う案を推奨するが、方式の確定は未了。SDK管理の場合はその旨を記録し、joseを維持する場合はJWKS形式の取得先と失効確認を別途確定する。X.509証明書マップをJWKSとして渡さない |
| 環境別の設定 | Firebase project ID、許可ドメイン、Backendの権限、メール確認・再設定の復帰先等を確定する |
| 初回tenantの作成・新規Caseの保存先 | 初回所属がない利用者でも登録処理へ到達できる順序を定める。利用者ごとに初期領域を設ける案は未確定であり、このADRで採用済みにはしない |
| 7日上限・失効の具体処理 | 検証済みauth_time等に基づくBackendの期限判定、失効確認の方法・反映時間、障害時の応答を定める。token更新で上限を回避できる設計にしない |
| Backend／Frontendの公開契約 | 現在利用者・登録状態・案件role・許可操作、招待、全端末ログアウト、未所属・期限切れ・権限変更時の応答を #90 と整合させる。新しいAPIが実装済みとは仮定しない |
| 本人Personの紐付け・アカウント連携 | ログインアカウントとCase内Personの紐付け、複数ログイン方法の連携・復旧を定める。氏名やメール一致だけで権限や利用者データを統合しない |
| 招待の実行契約 | 受諾時の再検証、並行操作・再試行、メール配送を具体化する。招待運用そのものは決定済み |
| 同意との接続 | 初回所属作成・招待受諾と、tenant配下の同意記録の適用範囲を #128 と整合させる |

## 既存設計への影響

- 従来の「Provider選定未確定」を、本ADRの採用方針に置き換える。Identity Adapterへの隔離は維持する。
- tenant claimを必須とする検証と、単一tenantを前提にした認証文脈を見直す。Backendによるtenant／Case membershipの確認を維持したまま、対象案件に応じた認可へ変更する。
- Issue #127の「tenant claimをFirestore membershipで裏取りする」は、「認証済みuidと対象tenant／CaseをFirestore membershipで裏取りする」へ更新する方針とする。
- Frontendとの契約は #90、実接続は #92 と連携する。本ADRの更新だけで、FrontendやBackendの実装が完了したとは扱わない。
- サービス間認証（Backend ↔ AI）は引き続き本ADRの対象外とし、#10で扱う。

## ADRの記録と実装・検証の区別

今回の成果物は、このADRへの判断内容の記録である。未決の技術案を新たな合意済み事項として扱わず、実装・検証は別作業として進める。

Issue #127全体の完了には、公開契約の確定と、stagingでの実token・鍵更新・期限切れ・失効・membershipによる認可の検証が残る。7日間の上限と、複数案件の権限分離も検証対象とする。

ADRを更新したことだけを理由に、実接続やstaging検証の完了条件を満たしたとは判断しない。
