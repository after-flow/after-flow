# バックエンドへの申し送り（2026-09-21 フロントエンド刷新分）

フロントエンドを作り直した際に、API・Rule Engine・エージェント側で対応や判断が必要になった項目をまとめます。
モック（`apps/web/src/mocks/`）は、ここに書いた動きを再現しています。
迷ったときは、モックの挙動を手本にしてください（特に `apps/web/src/mocks/rules.ts` と `apps/web/src/mocks/analysis.ts`）。

優先度：**高** = 法令・利用者の判断に関わるので公開前に必須／**中** = 体験が大きく崩れる／**低** = 改善

---

## 1. 【高】外国にある AI 事業者への提供の同意を、サーバー側でも強制する

- 同意画面では「AI事業者への提供（`CROSS_BORDER_AI`）に同意しない場合、書類の読み取りは使えない」と約束しています（個人情報保護法28条）。
- フロントエンドは、同意がない間は次の3つの入口を閉じています。ただし**画面側だけでは担保になりません**。
  - `POST /cases/:caseId/documents`（書類の追加 → AI 解析）
  - `POST /cases/:caseId/messages`（AIに相談）
  - `POST /tasks/:taskId/guidance/research`（窓口の自動調査）
- **依頼**：同意していない利用者からのこれらの要求は、AI 事業者へ送る前にサーバーで断ってください。
  - 例：`403` と `{ "code": "CONSENT_REQUIRED" }`。コード名が決まれば、フロントエンドで専用の案内を出します。
- 同意の版が上がった場合（`version` の変更）も、同じように未同意として扱ってください。

## 2. 【高】放棄前ロックの判定に使う「本人」を、ケースに持たせる

- **フロントエンドの判定（変更済み）**：財産処分・現金化にあたる導線（`assetDisposal: true` の手続き、契約の「名義を変える／解約する」）は、**ログインしている本人が単純承認を選んだと記録されるまで表示しません**。
  - 「全員が方法を記録した（`inheritanceDecision.decided === true`）」だけでは開けません。
  - 理由：相続放棄を選んだ人が財産を処分すると、放棄が認められなくなるおそれがあるためです（民法921条）。限定承認でも、財産の処分は家庭裁判所の手続きに沿って行います。
- **問題**：いまは「本人」を、ケースの入力者名（`Case.ownerName`）と相続人の名前が一致するかで見分けています。名前が変われば判定がずれます。
- **依頼**：`Case` に本人の相続人 ID（例：`ownerPersonId`）を持たせてください。
- **関連**：ケース作成の直後に、フロントエンドが `POST /cases/:caseId/persons` で本人を相続人として登録しています（作成画面の「私は相続人です」がオンのとき）。
  - ケース作成 API の中で同時に作ってもらえれば、この2回目の呼び出しは不要になり、途中で失敗して本人が登録されない状態もなくせます。

## 3. 【高】あてはまる手続きを漏れなく洗い出す（Rule Engine）

詳しい仕様は README「Rule Engine への依頼：あてはまる手続きを漏れなく洗い出す」にあります。要点は次のとおりです。

### 3-1. ケース作成の時点で手続きを用意する
- ご逝去日が入った時点で、`GET /cases/:id/tasks` と `/overview` に手続きと期限が載っている状態にしてください。
- 書類の解析を待たないでください（「死亡届まであと4日」を最初の画面で出すため）。

### 3-2. 故人の状況（`Case.profile`）で出し分ける（**API の追加**）
- ケース作成の直後の質問画面（`/cases/:id/setup`）から、`PATCH /cases/:id` で次を送ります。

```jsonc
{
  "dateOfBirth": "1945-04-02",        // null を送ったら「消す」
  "profile": {
    "healthInsurance": "NATIONAL | EMPLOYEE | LATE_ELDERLY | UNKNOWN",
    "pension": "EMPLOYEES | NATIONAL_ONLY | NONE | UNKNOWN",
    "occupation": "EMPLOYEE | SELF_EMPLOYED | NONE | UNKNOWN",
    "realEstate": "YES | NO | UNKNOWN",
    "car": "YES | NO | UNKNOWN",
    "mortgage": "YES | NO | UNKNOWN",
    "answeredAt": "2026-09-21T10:00:00.000Z"
  }
}
```

- `profile` は丸ごと送ります（部分更新ではなく置き換え）。
- 受け取ったら、あてはまる手続きを洗い出し直してください。
- **「わからない」・未回答**は、あてはまる可能性があるものとして手続きを残し、**`Task.conditional = true`** を立ててください（**型の追加**）。画面は「あてはまる場合」と添えます。
- 答えが変わってあてはまらなくなった手続きは、**まだ手を付けていないもの（`NOT_STARTED` かつ記録なし）だけ**消してください。
- 残す手続きの名前・説明・期限は、答えに合わせて直してください。ただし**窓口（`submitTo`）は、ルールが書いたままのものだけ**直してください。
  - 自律調査などで具体的になった窓口（「○○市役所 市民課」など）を、一般的な名前に戻さないでください。
- 洗い出す手続きは、新しいケースで最大28件です。条件と期限の一覧は README の表を参照してください。今回新たに加えた主なものは次のとおりです。
  - 不動産の相続登記（**2024年4月から義務・3年**）、遺言書の確認、相続人の確定、財産と借金の調査、遺産分割協議
  - 葬祭費／埋葬料、未支給年金、遺族年金、死亡一時金・寡婦年金、高額療養費、生命保険
  - 介護保険・後期高齢者医療の資格喪失、固定資産税の相続人代表者、自動車、団体信用生命保険、勤務先、個人事業の届出

### 3-3. 期限は法律の数え方で計算する（**誤りの修正**）
- **期間の初日は数えない**（民法140条）。例：9月15日から「14日以内」は9月29日まで。
- **月・年の期間は日数ではなく暦で数える**（民法143条）。例：9月15日から3か月は12月15日。応答する日がない月は末日（8月31日から3か月は11月30日）。
  - 以前のモックは3か月を90日として計算しており、相続の方法を決める期限が**2日早く**表示されていました。
- 死亡届は、発生日を含めて数えます（戸籍法43条）。
- **年金の受給停止は、厚生年金が10日・国民年金が14日**です（以前は一律14日）。種類が分からないときは10日に合わせてください。
- 「知った日」から数える手続き（死亡届・相続の方法・準確定申告・相続税・相続登記）は、`Case.knownAt` があればそれを起算日にしてください。以前はご逝去日で数えていました。
- `basisLabel` には、利用者が自分で数え直せる言い方（「亡くなった日の翌日から数えて14日以内」など）を入れてください。

### 3-4. 熟慮期間にも残日数を付ける（既存の依頼・未対応）
- `inheritanceDecision.deliberationDeadline` が日付だけのため、フロントエンドが残日数を計算しています。
- `DeadlineSummary` と同じ形で返してください。

### 3-5. 文言
- 相続税の説明は「財産の総額が基礎控除額以下なら申告は不要。ただし配偶者の税額軽減などの特例を使って0円になる場合は申告が必要」という一般的な決まりまでに留めてください（税理士法52条）。
  - 以前の「かからない場合は申告が不要なこともあります」は、申告漏れを招くおそれがあります。
- この手続き一覧と期限は、**公開前に司法書士・税理士・社会保険労務士に確認してもらってください。**
  - 14日の届出（世帯主変更・健康保険・介護保険）の数え始めは、モックでは早めに出る数え方にしています。

## 4. 【中】書類の読み取り（document_analysis）の約束

フロントエンドは実物の書類で確かめられていないため、次の約束に頼って動いています（README にも同じ内容があります）。

1. **`analysisStatus` は `ANALYZING` から `ANALYZED` か `NEEDS_REVIEW` に必ず変えてください。** 失敗した場合も `NEEDS_REVIEW` にしてください（撮り直しの案内が出ます）。
   - フロントエンドは、読み取り中の書類がある間だけ **3秒ごとに `GET /cases/:caseId/documents`** を取り直します。
   - この取り直しは、画面が裏に回っていても続けます（スマホで撮ったあと別のアプリに切り替える利用者が多いため）。
2. **確認（Approval）・気づき（Insight）・必要書類の更新を保存し終えてから、`analysisStatus` を変えてください。**
   - フロントエンドは状態が変わった瞬間に確認を取り直し、「AIからの確認に○件届いています」と件数を数えて知らせます。
   - 順番が逆だと「0件」と出てしまいます。
3. **確認には `sourceDocumentId` を必ず入れてください**（件数を書類ごとに数えるのに使います）。
4. **エラーは `code` で返してください。**
   - マイナンバー検知：`MY_NUMBER_DETECTED`（422）
   - 形式違い：`UNSUPPORTED_FILE_TYPE`（415）
   - 大きすぎる：HTTP `413`
   - これ以外は「うまく送れませんでした」と出ます。
5. **ファイルサイズの上限を決めて教えてください。** 画面に上限を表示し、送る前に止められるようにします。
6. **スマホの写真（HEIC）を受け付けるか決めてください。** 受け付けない場合は `UNSUPPORTED_FILE_TYPE` を返せば案内が出ます。
7. 複数の書類をまとめて選んだ場合、フロントエンドは**1枚ずつ順に** `POST` します。
8. 読み取った位置 `sourceBox` は、原本の幅・高さに対する割合（0〜1）で返してください。自信のない値には `confidence: 'LOW'` を付けてください。
9. 同じ書類の二重取り込みを検知したら、`possibleDuplicate` を付けてください。
10. 読み取った値が日付なら、`YYYY-MM-DD` で返してください（画面で「2026年9月15日」に直して表示します）。
11. **元の書類の表示**（画面は対応済み）：確認画面の左側と書類の詳細画面で、原本を表示します。main の `GET /cases/{caseId}/documents/{documentId}/content` を呼びます。
    - `application/octet-stream` のままで構いません。画面は先頭のバイトを見て PDF・PNG・JPEG を見分け、判断できなければファイル名の拡張子で判断します。
    - 読み取った位置の枠（`sourceBox`）は、画像のときだけ重ねます。PDF はページ内の位置が分からないため、枠は出しません。
    - HEIC（iPhone の写真）は多くのブラウザで表示できないため、画面は「保存して開く」を案内します。保存時に JPEG へ変換しておいてもらえると、そのまま表示できます。
    - 見つからない場合は 404、保存が終わっていない場合は 409 を返してください。画面は「表示できません」と出し、再試行はしません。
12. 書類の種類（`DocumentKind`）や状態を増やす場合、フロントエンドは知らない値を「その他」「読み取り前」として表示します（画面は落ちません）。

## 5. 【中】確認（Approval）の種類と反映

- **「故人の情報を更新する」提案の種類がありません。** モックの「故人の情報を登録する」（死亡診断書から氏名・死亡日を読み取ったもの）は、`TASK_PROPOSAL` として登録されています。
  - そのため画面のボタンが「この手続きを追加する」になり、内容と合いません。
  - 例：`CASE_UPDATE` のような種類を追加してください。追加されれば、フロントエンドで専用の文言を用意します。
- **手続き名を持たない提案を承認しても、名前のない手続きを作らないでください。**
  - 以前のモックはこれで空の手続きを作り、ほかを片づけたあとに「まずはこれ」に出てきていました（モックは修正済み）。
- フロントエンドは提案の種類ごとにボタン文言を変えています（書類のお願いなら「用意する書類に加える／いまは不要」など）。
  - 書類のお願い（`DOCUMENT_REQUEST`）を承認したら、どの手続きの必要書類に加えたかが分かるようにしてください（モックでは「相続人を調べる」に追加）。

## 6. 【中】エラーの返し方

- フロントエンドは、保存・記録に失敗すると画面の端に「保存できませんでした。通信の状態をご確認のうえ、もう一度お試しください。」と出します。
- **`409`（ほかの人が先に更新した）** は「ほかの方が先に内容を変えたため、保存できませんでした」と出し分けています。
  - 家族で同じケースを使う場合の競合は、409 で返してください。
- `401` はセッション切れとして、ログイン画面に戻します（既存どおり）。

## 7. 【中】ケース作成の入力チェック

- フロントエンドは、未来のご逝去日と、ご逝去日より前の「知った日」を止めています。
- 期限はすべてこの日付から数えるので、**サーバー側でも同じチェック**をしてください（`400` と、どの項目が違うかが分かる `code`）。

## 8. 【中】AI 相談（チャット）の回答

- 個別の法律・税務判断（「あなたは相続放棄すべき」など）を返さないよう、**サーバー側で止める仕組み**が必要です（弁護士法72条・税理士法52条）。
- 専門家への確認を促す注記は、フロントエンドでは `professionalNotice` フラグに頼っています。判断を含む回答でフラグが落ちていると、この担保が効きません。

## 9. 【低】自律監視（まだ無いもの）

画面側の受け皿（「AIの気づき」タブ、ホームの件数）はできていますが、次の検知はまだありません。

画面側は「前回からの続き」として、次の2種類の気づきを受け取れるようにしました。
- ホームの「前回からの続き」
- 手続きの画面の上の知らせ
- 一覧の「止まっています」の印

モック（`apps/web/src/mocks/watch.ts`）に、画面が想定している検知の規則を入れてあります。Backend／AI 側でも同じ規則で作ってください。

- **止まっている手続き**（`STALLED_TASK`）：型はありますが、main の Backend には検知する処理がありません（いま作られるのは `DEADLINE_RISK`・`MISSING_DOCUMENT`・`PROFESSIONAL_NEEDED` だけです）。
  - 提出して結果待ち（`SUBMITTED`／`WAITING_EXTERNAL`）のまま **14日**、更新がない
  - 進めている途中（`COLLECTING_INFORMATION`・`WAITING_DOCUMENTS`・`READY`・`ACTION_REQUIRED`）のまま **7日**、更新がない。期限まで7日を切っていれば **3日**
  - 未着手（`NOT_STARTED`）は対象外（期限が迫れば `DEADLINE_RISK` で知らせる）
  - `relatedTaskId` を必ず付けてください。画面はこれで手続きと結び付けます
  - 手続きが更新されたら、その知らせは取り下げてください（画面は、手続きを更新したら気づきを取り直します）
- **前提の変化**：既存の `INCONSISTENCY` で返してください（種類は増やしていません）。画面の表示名は「前提の変化・食い違い」です。
  - 相続人が増えた・減った：関係する手続き（`relatedTaskId`）は「相続の方法を決める」
  - 相続放棄を選んだ方がいる：次の順位の方が相続人になる場合がある。法律の判断を含むため `requiresProfessional: true`
  - はじめの家族の登録は、変化として扱わないでください。相続人が増えた・減ったを知らせるのは、誰かの相続の方法が記録された後、または「相続の方法を決める」の手続きに手を付けた後だけです

## 10. 【低】その他

- **使い方ガイドの「見た」の記録**：いまはブラウザに保存しています。家族で1台を共有すると2人目には出ませんが、「使い方を見る」からいつでも見られるので、急ぎではありません。
  - 利用者ごとに持ちたくなったら、ユーザー設定の API が必要です。
- **持ち物のチェック**（画面は対応済み）：手続きの画面で、持ち物を1つずつ押して「用意できた」を記録します。
  - 画面は `PATCH /tasks/:taskId` に `requiredDocuments`（全件）を送ります。
  - 案内（`guidance.bring`）にだけ載っている持ち物を押したときは、`id: 'bring_xxxxxxxx'` を付けて持ち物に加えます。
  - **main の契約との差**：main の `PATCH /cases/{caseId}/tasks/{taskId}` の `requiredDocuments` は `{ id, label, documentId }` だけで、**`collected` がありません**。紙の書類（印鑑・本人確認書類など）は `documentId` を持たないため、`collected` を足してください。
- **手続きの担当者の変更**（画面は対応済み）：手続きの画面で担当を選べます。一覧は担当で絞り込めます。
  - 画面は `PATCH /tasks/:taskId` に `assigneeId`（人の id。`null` で未定に戻す）を送ります。main の `assigneeId` と同じ意味です。
  - 応答の `assigneeName` は、人の登録から毎回引いてください（名前を直したとき・人を削除したときに追従させるため）。
  - 除外した人を指定されたら 409 を返してください（main の `ASSIGNEE_EXCLUDED` と同じ）。

## 11. 利用場面の精査で見つかったもの（追記）

### 11-1. 【高】期限の無い下準備に「目安の期限」を付ける
- 「相続人を調べる（戸籍の収集）」「財産と借金を調べる」「遺言書があるか確かめる」には法律上の期限がありません。
  - そのため期限の順に並べると一番後ろに回り、ホームにも出てきません。
  - しかしこれらは**3か月以内に相続の方法を決めるための前提**で、戸籍の取り寄せには数週間かかります。
- **フロントエンドの応急処置**：段階が `investigation` で期限の無い手続きを「早めに」と表示しています。
  - 並び順は「相続の方法を決める」の期限の手前にし、ホームの「そのあとにやること」にも出します。
- **依頼**：Rule Engine で、法律上の期限とは別の**目安の期限**を返してください。
  - 例：`Task.targetDate`（`DeadlineSummary` と同じ形で、`critical: false`・`basisLabel`「相続の方法を決める期限に間に合わせるための目安」）。
  - 目安は、たとえば相続の方法を決める期限の1か月前です。
  - 返ってくるようになれば、フロントエンドの応急処置（段階名での判定）は外します。

### 11-2. 【中】「この手続きは不要だった」を記録できるようにする
- 「あてはまる場合」の手続きが不要だと分かっても、いまは「完了」にするしかありません。
  - 完了にすると「済んだ」に入り、やったことになってしまいます。
- **依頼**：手続きの状態に「不要」（例：`NOT_APPLICABLE`）を追加してください。
  - 状態を変える API は既存の `PATCH /tasks/:taskId` で構いません。
  - 答え直しでの洗い出し（3-2）で消してよい対象からは外してください。利用者が決めたことなので残します。
- 追加されれば、フロントエンドで「不要だった」ボタンと「不要」タブを用意します。

### 11-3. 【中】財産・借金・契約の削除、金額の消去
- フロントエンドに「直す」を付けました（既存の `PATCH /assets/:id`・`/liabilities/:id`・`/contracts/:id` を使用）。
- **金額を空にしたときは `amount: null` を送ります。** `null` は「金額を消す」として扱ってください。
- **依頼**：二重に登録したものを消せるよう、削除の API を追加してください（`DELETE /assets/:id` など）。

### 11-4. 【中】読み取れなかった書類の種類を、利用者が選べるようにする
- 「内容の確認が必要」（`NEEDS_REVIEW`）になった書類は、いまは撮り直して追加し直すしかありません。暗い場所で撮った戸籍などで、高齢の方が何度も撮り直すことになります。
- **依頼**：書類の種類を変える API（例：`PATCH /documents/:id` で `kind` を送ると `kindSource: 'MANUAL'`）と、読み取り直しの API（例：`POST /documents/:id/analyze`）を追加してください。

### 11-5. 【低】完了の記録に写真を添付する
- 窓口でもらう受理証明や控えは紙なので、その場で写真に撮って残すのが自然ですが、いまの記録（`Evidence`）は文字だけです。
- **依頼**：記録に書類をひも付けられるようにしてください（例：`Evidence.documentId`）。書類そのものは既存の書類の追加 API で送ります。

### 11-6. 【中】葬儀・火葬が済んだかを、利用者が記録する
- 葬儀・火葬は手続きとして登録されないことが多く、手続きの件数からは「済み」にできません。
  - これまでフロントエンドでは「③〜⑤の段階に進んだら済みとみなす」と推定していましたが、推定はやめました。
- **仕様**：手続きの流れの「葬儀・火葬」の段階は、利用者が「葬儀・火葬が済んだ」を押して記録したかどうかだけで済みとします。取り消しもできます。
- **依頼**：ケースに `funeralCompletedAt`（日時。`null` は「まだ」）を持たせ、`PATCH /cases/:caseId` で受け取って `Case` で返してください。
  - `null` を受け取ったら記録を消してください（「まだ済んでいない」に戻す操作です）。
  - `GET /cases/:caseId/overview` の `flowStages` の `funeral` の `state` も、この記録で `COMPLETED` にしてもらえると、画面側の判定を外せます（いまは画面側で `case.funeralCompletedAt` を見ています）。

## 付録：フロントエンドが呼んでいる API の変更点

| API | 変更 |
| --- | --- |
| `PATCH /cases/:caseId` | `municipality` に加えて、**`dateOfBirth`（`null` で消す）・`profile`・`funeralCompletedAt`（`null` で消す）** を送る。受け取ったら手続きを洗い出し直す |
| `POST /cases/:caseId/persons` | ケース作成の直後に、本人を相続人として登録するために呼ぶ（2 の依頼で不要にできる） |
| `GET /cases/:caseId/documents` | 読み取り中の書類がある間、3秒ごとに呼ぶ（画面が裏でも） |
| `GET /documents/:id` | 読み取り中の詳細画面を開いている間、3秒ごとに呼ぶ |
| `GET /tasks/:id` | 自律調査中は2秒ごとに呼ぶ（既存どおり。5分で打ち切り） |
| 型 `Case` | `profile?: CaseProfile`・`funeralCompletedAt?: string \| null` を追加 |
| 型 `Task` | `conditional?: boolean` を追加 |
| `PATCH /assets/:id`・`/liabilities/:id` | 「直す」から呼ぶ。**`amount: null` で金額を消す** |
| `PATCH /contracts/:id` | 「直す」から、名前・種類・契約先を送る |
| `GET /cases/:caseId/documents/:documentId/content` | **新たに呼ぶ**。原本を表示する（main にある API と同じ道筋） |
| `PATCH /tasks/:taskId` | **`requiredDocuments`（持ち物のチェック）・`assigneeId`（担当）** も送る |
| `GET /cases/:caseId/insights` | 手続き・人・相続の方法を更新した後にも取り直す（止まっている知らせの取り下げ、前提の変化の受け取り） |
